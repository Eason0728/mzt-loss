## 排 Phase 的原則

這支專案最大的風險**不是技術，是「會不會又變得太複雜」**——上一版就是這樣被放棄的。
所以 Phase 的排法是：**把「能不能真的用」這件事盡量提早驗證**，雲端與統計往後放。

Phase 1 結束時你就能在手機上實際打一天看看；不好用就在那裡改，改到順了才接雲端。

## 四個 Phase

| Phase | 里程碑（做完你能做什麼） | 任務 | 完成前不做 |
|---|---|---|---|
| **1. 能打** | 手機開本機檔案就能登記、能維護成本表，資料先存手機本機 | T1–T5 | 不碰 Google、不寫統計 |
| **2. 能看** | 統計頁能算出期間金額、三張排行、走勢、CSV、列印 | T6–T7 | 不碰 Google |
| **3. 能同步** | 資料上雲端試算表，多台裝置同一份，斷線可補送且不重複 | T8–T9 | 不做部署 |
| **4. 能上線** | 端對端測試綠燈，前端上 GitHub Pages、後端上 Apps Script | T10–T11 | — |

### Phase 1（能打）

- 純前端，資料全部存 localStorage，開 `index.html` 就能用。
- 完成後**先給你試用**：把 build 出來的單一 HTML 傳給你，你存到手機、實際打幾筆。
- **這裡是最重要的檢查點**——不好用就停下來改，不要往下做。

### Phase 2（能看）

- 統計仍然只吃 localStorage 的資料，先把畫面與算法做對。
- 統計全部由 `calc.summarize()` 純函式算，好測。

### Phase 3（能同步）

- 先做後端 `Code.gs` 與試算表，再改前端的 `api` 模組。
- localStorage 從「正本」降級成「快取 ＋ 待送佇列」。
- 這個 Phase 的重點不是功能，是**不重複、不掉資料**。

### Phase 4（能上線）

- 補 Playwright 端對端測試。
- 部署三件事：新開試算表、clasp 推 Apps Script 並「部署新版本」、開 GitHub repo 並啟用 Pages。
- **鐵律 1**：這三件事我都會先問過你才做。

## 技術決定摘要（細節在 spec.md）

| 決定 | 理由 |
|---|---|
| 前端三個檔（html／css／js）＋ 30 行 `build.py` 合成單一檔 | 舊版把 HTML 塞進 88KB 的 Python 字串，難改難比對差異 |
| 所有計算在前端，後端只存取 | 後端一開始算錢就會出現第二個計算點 |
| 金額只在 `makeRecord()` 算一次 | 舊版的一號設計約束，繼續沿用 |
| `loss` 存單位成本與金額的快照 | 改單價不能動到上個月報表 |
| id 由前端產、格式 `L-<14 碼時間>-<8 碼隨機>` | 送出失敗重按不會變兩筆 |
| 打錯用「作廢」標記，不刪列不改數字 | 保留稽核軌跡，統計排除 |

## 停損訊號（出現就停下來找你，不要硬做）

1. Phase 1 試用後你覺得「還是太複雜」→ 停止往下，回頭砍功能，不要帶著問題接雲端。
2. Apps Script 部署後 `bootstrap` 打不通超過兩輪 → 停下回報，不要盲改。
3. 任何一個任務做到超出 200 行還沒收斂 → 代表切得不對，回來重切。
